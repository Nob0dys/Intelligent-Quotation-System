## 一、现状与差距

### 1.1 现在能怎么改数据

| 入口 | 能力 | 位置 |
|---|---|---|
| 数据资产 → 价目导入 | 上传价目本**批量新增**；重复行跳过 | `main.py:1536` `_read_history_upload` → `main.py:1590` `_insert_history_rows` |
| 历史报价 → 手工录入 | **单条新增** | 前端 `QuoteApp.tsx:1236` `HistoryEntryModal` → `POST /api/history`（`main.py:1318`） |
| 数据资产 → 质量治理 | 一键**去重**（合并重复行） | `POST /api/governance/dedup-history` |
| 数据资产 → 数据库 | 只改**库的元数据**（中文名/备注/标签），不碰价目数据 | `PATCH /api/databases/{key}` |

### 1.2 差距（也就是你这次要的）

- **改不了已有行**：没有任何接口能修改一条已存在的价目记录。
- **删不了行**：`history_quotes` 没有删除接口（去重是合并，不是删除）。
- **没有表格视图**：历史报价页是"搜索 → 卡片列表"（`QuoteApp.tsx:1210` `HistorySearch`），一次最多 30 条，看不了全表，也没法逐格编辑。
- **改完必须手动补派生字段**：每行有 5 个 `normalized_*` 派生列 + `data_quality`，见 §四。

### 1.3 三个必须先知道的机制（否则改了不生效）

1. **派生列参与匹配打分**。`history_quotes` 每行存了 `normalized_name / normalized_spec / normalized_product_code / normalized_model / normalized_unit`（`models.py:69-93`）与 `data_quality`。它们由 `normalize_text()`（`matching.py:69`）算出。**只改 `name` 不改 `normalized_name`，界面看着变了、匹配结果不变**——这是最容易埋的坑。
2. **匹配结果有进程级缓存 + 版本号失效**。`matching.py` 里多个 `lru_cache`（最大 1048576），靠 `SystemMeta.history_version` 失效：任何数据写入都必须调 `bump_history_version()`（`services.py:277`）+ `clear_match_caches()`（`matching.py:231`）。现有 4 处写入都调了（`main.py:1349 / 1463 / 1530 / 1616`）。
3. **导入的原始 Excel 文件不保留**。`_read_history_upload` 把上传写到 `data/tmp/` 解析后**立即删除**（`main.py:1553`）。所以今天无法"写回原文件"。

> **实施阶段的两处更正（写方案时的判断不准确，实测后已改口）**
>
> - **第 1 条说反了**：`matching.py` 打分读的是**原始业务列**（`record["name"]` / `record["spec"]` …，见 `matching.py:1030-1045`），归一化在打分时用带缓存的纯函数现算。`normalized_*` 目前只服务治理口径（`governance_summary` 按 `normalized_name` 归组）。所以"只改业务列不重算派生列 → 匹配不变"**不成立**；真正的影响是治理页面的重复/冲突分组会用到旧口径。统一重算仍然照做，理由改成"口径一致 + 为将来切预计算打分留路"。
> - **第 2 条不成立**：`clear_match_caches()` 定义在 `matching.py:231` 但**从未被调用**，`get_history_version()` 也**没有任何读取方**——版本号机制实际是死代码。原因见上：`matching` 的 `lru_cache` 全部是"入参 → 出参"的纯函数缓存（`normalize_text` / `bigram_dice` / `parameter_similarity` / `_spec_features` …），数据变了缓存也不会算错。而 `process_job` 每次报价都从库里**重新 `select(HistoryQuote)`**（`services.py:478`），不存在"报价池缓存"。
> - **顺带纠正一条**：`history_quotes.data_quality` 是**只写不读**的展示列——匹配时 `matching.py:1044` 用自己的字段集合重算一份，不读库里的值；前端与导出也都没读它。所以统一它的算法是安全的。
> - **新增的必须知道项**：网格里的 `price` 是**不含税基准价**。表头写"含税单价"的价目本在导入时已按固定税率折算（`excel_service.py:426-443`），导出报价时再乘回 `tax_rate`。网格必须标注"不含税"，否则用户按含税价改会让报价整体低一个税点。

## 二、整体方案概览

分三层，对应你的三句话：

```
① 打开 ──→ ② 编辑 ──→ ③ 保存/同步
   │           │            │
   │           │            ├─ 同步回数据库（核心，单事务 diff 落库）
   │           │            └─ 另存为 .xlsx / .csv
   │           │
   │           └─ 网格内自由增删改查（行内编辑、多选粘贴、撤销、查找替换、筛选排序）
   │
   ├─ 直接打开「某个库的价目表」（主路径，不需要 Excel 文件）
   └─ 或先导入 .xlsx / .xls / .csv 作为起点
```

**关键设计取向：数据库是唯一真源（single source of truth），Excel 文件只是进出的载体。**

不采用"打开本地 .xlsx → 编辑 → 整表覆盖数据库"的思路，原因：

- 整表覆盖会丢掉数据库里不在该文件中的记录（例如另一个来源导入的行）；
- 无法区分"这行是用户删的"还是"这个文件本来就没有"，删除语义会丢失；
- 一次误操作就是全表覆盖，不可回溯。

改为**变更集（diff）同步**：前端记录"新增了哪几行、改了哪几行的哪几个字段、删了哪几行"，只把变更发给后端。这样删除有明确语义、可审计、可只回滚一部分。

## 三、可支持的文件格式

| 方向 | 格式 | 现状 | 说明 |
|---|---|---|---|
| 导入进网格 | `.xlsx` / `.xlsm` | **已支持** | `parse_history_workbook()`（`excel_service.py:401`），遍历所有 sheet，表头别名识别（`PRICE_ALIASES` 等） |
| 导入进网格 | `.xls` | **已支持**（需 `xlrd`） | 同上，走 `open_workbook()` 分支 |
| 导入进网格 | `.csv` | **需新增** | 现在显式拒绝：`raise ValueError("仅支持 .xlsx / .xlsm / .xls 文件")`（`excel_service.py:314`）。CSV 无表头别名/多 sheet 概念，需单写一个轻量解析器（约 40 行） |
| 导出 | `.xlsx` | **需新增**（后端） | 后端已有 openpyxl，写一个"价目表 → 工作簿"的函数即可 |
| 导出 | `.csv` | **需新增** | 注意 Excel 打开 UTF-8 CSV 的中文乱码问题：写 **UTF-8 with BOM**（`utf-8-sig`） |
| 写回原 `.xlsx` 文件 | — | **需新增**，见 §七 | 浏览器不能任意写本地文件，有三种落地方式 |

**格式与列名约定**：导出/导入的表头统一用中文业务列名（`货物名称 / 参数 / 型号 / 产品编码 / 品牌 / 制造商 / 单位 / 数量 / 单价 / 报价日期`），与现有导入解析器的别名表对齐，保证"导出再导入"能闭环。

## 四、编辑范围（字段级）

`history_quotes` 的列按可编辑性分三类：

### 4.1 可编辑（业务字段，10 个）

| 列 | 中文表头 | 类型 | 校验 |
|---|---|---|---|
| `name` | 货物名称 | 文本 | **必填**，去首尾空白后非空 |
| `spec` | 参数 | 长文本 | 可空 |
| `model` | 型号 | 文本 | 可空 |
| `product_code` | 产品编码 | 文本 | 可空；纯数字串需保留前导零（已有 `normalize_standard_code`，见 `excel_service.py:482`） |
| `brand` | 品牌 | 文本 | 可空 |
| `manufacturer` | 制造商 | 文本 | 可空 |
| `unit` | 单位 | 文本 | 可空 |
| `quantity` | 数量 | 数值 | 可空，≥0 |
| `price` | 单价 | 数值 | **必填**，≥0（匹配按价格算分） |
| `quote_date` | 报价日期 | 文本 | 可空 |

### 4.2 只读 · 后端自动重算（6 个）

`normalized_name`、`normalized_spec`、`normalized_product_code`、`normalized_model`、`normalized_unit`、`data_quality`

- **不允许在网格里编辑**，保存时由后端根据 4.1 重算。
- `data_quality = 非空质量字段数 / 质量字段总数`，质量字段现为 `[spec, model, manufacturer, unit, product_code, source_file]`（`main.py:1587`）。
- 这一条是硬约束：**派生列必须与业务列在同一次保存里重算**，否则匹配会静默错乱。

### 4.3 只读 · 系统与溯源（6 个）

`id`、`source_file`、`source_sheet`、`source_row`、`source_priority`、`created_at`

- 网格中**可显示但不可编辑**（用于溯源："这行是从哪个文件的哪个 sheet 哪一行来的"）。
- `id` 的生成规则：导入行为 `{文件名}:{sheet}:{行号}`，手工录入为 `manual:{uuid}`。**编辑保留原 id**（这样才能 UPDATE 而不是 INSERT）；新增行由后端生成 `manual:{uuid}`。
- `source_priority` 参与搜索排序（`main.py:1297`），保留原值。

### 4.4 范围之外（本期不做，但可扩展）

客户档案、报价任务、用户账号目前都**不纳入**表格编辑。若后续要，同一套"网格 + 变更集同步"骨架可以复用，只是每张表的可编辑列与校验规则不同——建议那时把校验规则抽成"表级 schema 描述"再复用。

## 五、交互方式

### 5.1 视图与导航

- 落点：**数据资产 → 价目导入** 升级为 **价目数据**，或在 4 个 Tab 中新增第 5 个 **表格编辑**。推荐后者（导入是"一次性动作"，编辑是"持续工作台"，混在一起会让导入的结果反馈和编辑的脏状态互相干扰）。
- 顶部先选**库**（复用现有 `DatabasePicker` 的最近常用 + 搜索逻辑，含 `database_key`），因为现在支持多库并存。

### 5.2 网格能力

| 能力 | 交互 | 优先级 |
|---|---|---|
| 浏览全表 | 虚拟滚动（4000+ 行 × 20 列不卡） | P1 |
| 行内编辑 | 双击进入编辑；`Enter` 确认并下移；`Tab` 确认并右移；`Esc` 取消 | P2 |
| 新增行 | 底部"＋ 新增一行"，或最后一格 `Tab` 自动追加 | P2 |
| 删除行 | 行首勾选 → "删除选中"；支持多选 | P2 |
| 复制/粘贴 | 选中区域 `Ctrl+C/V`；**支持从 Excel 直接粘贴多行多列** | P3 |
| 撤销/重做 | `Ctrl+Z` / `Ctrl+Shift+Z`，前端操作栈（建议 50 步） | P3 |
| 查找/替换 | 顶部查找框 + 批量替换（可选"仅替换筛选结果"） | P3 |
| 筛选/排序 | 按列筛选、点击表头排序（前端内存排序） | P3 |
| 列宽/冻结 | 拖拽列宽、冻结首列 | P3 |
| 脏标记 | 改动过的行/格高亮；顶部显示"未保存 N 处改动" | P2 |
| 保存/放弃 | "保存到数据库" / "放弃更改"（放弃前二次确认） | P2 |
| 校验提示 | 单元格红框 + 悬浮说明；保存前汇总 | P2 |

### 5.3 分页 vs 全量加载

- 推荐：**分页拉取（每页 500 行）+ 前端虚拟滚动**，而不是一次拉 4000+ 行。
- 但"筛选/排序/查找替换"如果要作用于全表，就得全量。折中：**默认分页浏览；"全表模式"按需加载**（4000 行约 1–2 MB JSON，本地部署可接受）。
- 变更集不依赖分页：即使用户跨页编辑，dirty 集合仍按 `id` 累积。

## 六、保存与应用（核心）

### 6.1 变更集协议

```
POST /api/history/bulk-edit
{
  "database_key": "db_db42f474",          // 目标库；不传 = 当前激活库
  "created": [
    { "client_ref": "new-1", "name": "...", "spec": "...", "price": 12.5, ... }
  ],
  "updated": [
    { "id": "赛特尔25年.xls:初中物理:12", "revision": 3, "changes": { "price": 15.0, "brand": "群信" } }
  ],
  "deleted": [
    { "id": "manual:xxx", "revision": 1 }
  ]
}
```

响应**逐行返回**，不整体成败：

```
{
  "ok": true,
  "applied": { "created": 2, "updated": 5, "deleted": 1 },
  "results": [
    { "client_ref": "new-1", "status": "ok", "id": "manual:8f3c..." },
    { "id": "赛特尔25年.xls:初中物理:12", "status": "conflict",
      "detail": "该行已被他人修改（服务端 revision=5）", "server": { ... } },
    { "id": "manual:xxx", "status": "rejected", "detail": "单价必须 ≥ 0" }
  ],
  "skipped_duplicates": 1
}
```

前端据此把失败行标红、保留未保存状态，成功行清掉 dirty 标记。

### 6.2 服务端处理顺序（**单个事务**）

```
1. 解析 database_key → session_for_key(key)（复用 B1 的独立引擎，不干扰全局激活库）
2. 保存前自动备份该库文件到 data/_backup/（复用 registry 的备份机制）
3. 逐行校验：
   - created: name 非空、price 数值 ≥0、长度上限
   - updated: id 必须存在；revision 必须匹配（乐观锁）
   - deleted: id 必须存在
   - 收集错误，标记该行 rejected，其余行继续
4. 重算派生：normalized_* = normalize_text(业务列)；data_quality = 非空占比
5. 去重检测：用 history_dedup_key(name, spec, unit, manufacturer, price)（services.py:238）
   - 与库中已有行撞键 → 按策略处理（见 §6.3）
6. 落库：db.add(...) / setattr / db.delete(...)
7. bump_history_version(db) + clear_match_caches()   ← 漏了这一步改完不生效
8. audit(db, user_id, "history.bulk_edit", "history_quote", key,
         {"created": n, "updated": n, "deleted": n, "fields": {...字段级摘要...}})
9. db.commit()
```

### 6.3 去重冲突策略（需要你拍板，见 §十一）

| 策略 | 行为 | 适用 |
|---|---|---|
| A. 拒绝（默认） | 撞键的 `created` 行标 rejected，提示"与第 X 行重复" | 最安全，用户自己决定 |
| B. 跳过 | 静默跳过撞键行，计入 `skipped_duplicates` | 与现有导入行为一致 |
| C. 合并 | 撞键则更新已有行 | 便利但有误覆盖风险 |

推荐 **A**，并在提示里给出冲突行的定位（可点击跳转），因为这正是"治理"想要的语义。

### 6.4 冲突处理（乐观锁）

`history_quotes` 目前**没有** `updated_at` / `revision` 列，无法判断"我拿到的这行是否已被他人改过"。需要补一列：

- 新增 `revision: int`（默认 1）或 `updated_at`（`DateTime`），走现有的轻量迁移框架 `_apply_lightweight_migrations()`（`database.py`，已支持 `ALTER TABLE ADD COLUMN`）。
- 每次更新 +1。前端拉取时带上，保存时回传；不匹配 → `conflict`，返回服务端当前值让用户选择"覆盖 / 放弃"。

单机单用户场景下冲突很少，但**多库并存后两个人同时编同一个库**是会发生的，这一列成本很低、收益明确。

### 6.5 保存前自动备份

复用 `registry` 已有的备份机制（删除库时会备份到 `data/_backup/`，见 `registry.trash_entry`）。批量编辑前对目标库文件做一次带时间戳的拷贝，例如：

```
data/_backup/quote-20260921-173000.db
```

这样任何一次误操作都能人工回滚。**注意**：需要先 `dispose_key()` 释放该库的独立引擎再拷贝，否则 Windows 下可能拷到未落盘的 WAL 数据（`database.py` 已有 `dispose_key`）。

### 6.6 单次变更上限

设一个上限（例如单次 5000 行 / 事务），超限直接拒绝并提示分批。避免一个超长事务把 SQLite 写锁持太久。

## 七、"保存回 Excel 文件"的三种落地方式

你的原话是"保存或同步回数据库"，这里把"保存到文件"的选项摊开：

| 方式 | 能做到什么 | 限制 | 建议 |
|---|---|---|---|
| **A. 下载新文件** | 把当前网格导出为 `.xlsx` / `.csv` 下载 | 是"另存为"，不是写回原文件 | **默认方案**，全平台可用 |
| **B. File System Access API** | 浏览器里**真正写回用户选定的那个 .xlsx**（`showSaveFilePicker` / `showOpenFilePicker` + `createWritable`） | 仅 Chromium（Chrome/Edge）；首次需用户授权选文件；Firefox/Safari 不支持 | **推荐**：本地部署正好就是 Chrome/Edge，可以做到"打开原文件 → 编辑 → 保存回原文件"的完整体验 |
| **C. 后端保留源文件并回写** | 服务端自动把结果写回源文件，用户无感 | 需改导入流程**留存**原始文件（现在 `main.py:1553` 解析后即删）；且只对"由文件导入的行"有效，手工行无处可写 | 仅在你需要"服务器定时导出"时做 |

**推荐组合**：默认 A（导出下载）；需要"编辑原表"时用 B。B 与 A 可以共用同一个"网格数据 → xlsx 二进制"的生成函数——前端已有 `exceljs` 依赖（`package.json`，目前只被 `scripts/build-history.mjs` 使用），做客户端生成不需要新增任何依赖。

> 关于公式与格式：无论 A/B/C，**同步的都是"值"**。现有解析器读取的是 Excel 的计算结果值（`excel_service.py:420` 附近的缓存值处理），回写不会保留原公式、合并单元格、条件格式。如果这些对你重要，需要走 §九 的 Univer 路线。

## 九、技术选型（表格组件）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|

## 十五、二期：打开本地 Excel（2026-09-21 已落地）

一期把"网格"做成了对着数据库编辑，但你最初的原话是「**能够直接打开一个 Excel 表格文件**，在表格中自由地对其中任意数据进行增删改查」。二期把**文件入口**补上，形成完整闭环：

```
打开本地 Excel → 逐行比对预览 → 用户确认 → 应用（写库）→ 网格刷新
```

### 15.1 为什么不直接改文件、也不整表覆盖

数据库是唯一真源，Excel 只是进出的载体。所以：

- **不写回原 .xlsx**（决策 ③）：文件只是"输入"，改动落在库里。
- **不做整表覆盖**：整表覆盖会丢掉"不在这个文件里的行"，也表达不了"删除"。所以只发**变更集**（新增 / 修改 / 删除三类行），复用一期已经做好的 `POST /api/history/bulk-edit`——校验、乐观锁、去重、备份、审计全在那条通道上，二期**没有**新开第二条写入路径。

### 15.2 接口：`POST /api/history/open-file`

**只解析比对，绝不写库**（有测试守着：调用前后库里行数与 `revision` 完全不变）。参数 `file` + `database_key`，管理员权限。

返回逐行建议动作：

| 动作 | 含义 | 是否写入 |
|---|---|---|
| `create` | 库里没有同一器材 | 会新增 |
| `update` | 库里恰好一条同一器材且文件与它不同（`changed` 列出差异） | 会修改 |
| `unchanged` | 库里恰好一条且完全一致 | 不写 |
| `ambiguous` | 库里多条同一器材，`targets` 给候选（每个候选都已算好合并结果） | 需用户指定 |
| `duplicate` | 文件内前面已出现同一器材，**或**与前面某行指向库里同一条记录 | 不写 |
| `invalid` | 该行没有有效价格，或所在 sheet 根本没有价格列 | 不写 |

### 15.3 两个必须讲清楚的规则

**① 按表头判断"文件提供了哪些字段"，不能按单元格是否为空。**

- 文件**有**品牌列但这一行空着 = 用户想清空 → 真的清空。
- 文件**根本没有**品牌列 = 用户不关心 → 更新时保留库里的原值。

混淆这两个会把库里已有的品牌/制造商**静默清空**。所以 `_workbook_provided_fields()` 按表头取字段集合，合并时只覆盖文件确实提供的字段。

**② 匹配只用文件确实提供了的身份字段。**

身份键是（名称, 参数, 单位, 制造商）——恰好是去重键 `history_dedup_key` 的**前四项**（不含价格）。不含价格，才能把"同一器材改了价"认成 `update` 而不是新增一条重复记录。

但**实施中发现一个真 bug**：身份键含制造商，而价目本常常没有制造商列。此时文件行算不出完整四元组（制造商只能算成空串），拿空串去和库里"制造商=某某厂"的行比**永远比不上**，于是"更新这一行"被误判成"新增一条"，一保存库里就多出重复行。

修法：`history_rows.identity_projection(values, fields)` 支持按**字段子集**算身份键，比对时只用文件确实提供了的那些身份字段。字段越少匹配越松（缺制造商列就退化成名称+参数+单位），撞上多条就报 `ambiguous` 交给用户指定，**绝不在这里猜**。实际用了哪几个字段在 `match_fields` / `match_labels` 里回传，前端显示成「按 名称/参数/单位 匹配」。

取舍说明：文件带了制造商列时仍用严格四元组匹配。宁可多报一条可见的"新增"让用户自己决定，也不要悄悄合并到一条不相干的行上——**过度合并会静默改数据，误判新增至少看得见**。

顺带补了一个保护：两个 sheet 列不同 → 身份键不同 → 但可能指向库里同一条记录，第二条会被判 `duplicate`（"与文件中第 N 行指向库里的同一条记录"）。否则保存时两行去改同一条，第二行必然撞乐观锁，用户看到的是莫名其妙的"版本冲突"。

### 15.4 前端

「表格编辑」Tab 工具栏加「打开本地 Excel」（管理员可见，`accept=".xlsx,.xls,.xlsm"`），弹出预览对话框：

- 顶部：文件名、总行数、会改动行数、目标库；明确提示"**这一步只是比对，没有改动数据库**"。
- 分组切换：**将改动 / 无需改动 / 不载入**，默认停在"将改动"。
- **逐行勾选**：「将改动」组每行带复选框（另有"全选 / 全不选"），勾掉的行灰显、标注"已排除，这次不写"。一份价目本常混着暂时不想动的新品，**全有或全无的确认不算确认**。
- 每行显示：动作标签、器材名、来源（文件·sheet·行号）、**按哪几个字段匹配上的**、比对原因、以及只列真正变化字段的前后对比（`旧值 → 新值`）。
- `ambiguous` 行内嵌候选单选，每个候选显示单价、来源位置、版本号、以及"选它会改什么"；同时把这行自己在文件里的值也列出来（否则只剩一个行号，用户认不出是哪件器材）。
- 底部：**「应用并保存（N）」的 N 是"点下去实际会写几行"**——已排除的行、以及「需指定」还没选的行都不算进去。所以 N 会随勾选和候选选择实时变化，永远等于真正提交的行数；有未选的 `ambiguous` 行时会二次确认。

点「应用并保存」后把"会改动"的行转成 `{created, updated, deleted:[]}` 调 `bulk-edit`；冲突行（版本过期 / 去重冲突）回落到**一期已有的问题面板**，带"跳到该行"。未保存的网格改动不会被这次应用一起提交，应用前会明确告知。

## 十七、四期：上传 500 修复 + 「命名 / 上传」合并成一张创建卡片

### 17.1 现象与误判风险

用户报「无法上传数据集」。实测复现：`POST /api/databases/{key}/import` → **500 Internal Server Error**，且 `data/tmp/` 里堆了 4 个没被删掉的 `import-*.xlsx`（用户 4 次尝试的原始文件，每个 109856 字节）。

最容易误判的一点：**文件本身完全正常**。拿其中一个残留文件直接喂 `parse_history_workbook()`，解析出 **822 条、其中 821 条有有效价格**。所以"上传失败"与 Excel 无关。

### 17.2 根因（证据链）

后端窗口的 stderr 给出了完整栈：

```
main.py:2652  import_into_database
main.py:2320  _read_history_upload
main.py:2315  temp_path.unlink(missing_ok=True)      ← 崩溃点
  → shim/sitecustomize.py:1168 _safe_path_unlink
  → shim/sitecustomize.py:967  _try_trash
  → shim/sitecustomize.py:851  _check_bulk_delete_guard
  → shim/sitecustomize.py:826  raise SystemExit(1)

[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":230,"threshold":50,"scope":"turn",...}
```

**不是文件锁，也不是解析错误**。定位过程刻意排除了干扰项：

| 假设 | 验证方式 | 结论 |
|---|---|---|
| 文件被占用（Windows 锁） | 新进程删那个"服务删不掉"的临时文件 | **能删掉** → 不是文件锁 |
| `CODEBUDDY_TOOL_CALL_ID` 过期 | 用假 call id 跑 unlink | 仍成功 → 不是 id 过期 |
| 删除被安全策略拦截 | 读后端进程 stderr | **命中**：`SystemExit(1)` |

真实机制：后端是**长驻进程**，启动时继承了工具调用环境注入的 safe-delete guard 环境变量；它每次删除都要向 guard"报账"，而本轮删除计数（230）已超过阈值（50），guard 直接拒绝并抛 `SystemExit`。

### 17.3 真正的缺陷：清理失败不该否决业务结果

环境是外因，**代码缺陷是内因**——`finally` 里的收尾清理抛异常，把一次成功的导入变成 500：

```python
finally:
    temp_path.unlink(missing_ok=True)   # ← 异常从这里冒泡，HTTP 200 变 500
```

而且崩溃点在**解析结束、写库之前**（`_import_history_rows` 在下一行才调用），所以数据**一条都没进去**——用户看到"上传失败"，会合理地怀疑自己的文件坏了。

同一个缺陷在 `main.py` 里有 **4 处**（导入临时文件、超限上传回滚、删任务时删源文件、备份轮转），`registry.py` 的 `purge_entry` 还有 2 处。

### 17.4 修复

新增一个"删不掉也不许冒泡"的收尾清理，并统一替换 4 处 `unlink`：

```python
def safe_unlink(path: Path) -> bool:
    """尽力删除文件，返回是否删成功。清理是收尾动作，绝不能反过来把一次成功的
    业务操作判成失败。所以连 BaseException 一起兜住，失败只记日志、不冒泡。"""
    try:
        path.unlink(missing_ok=True)
        return True
    except BaseException as exc:  # noqa: BLE001
        logger.warning("文件清理失败（不影响本次操作结果）：%s（%s: %s）", path, type(exc).__name__, exc)
        return False
```

配套：
- `sweep_stale_import_temps()`：导入前顺手清掉超过 `QUOTE_IMPORT_TMP_TTL_HOURS`（默认 6 小时）的 `import-*` 残留，best-effort、失败即跳过 —— 解决"删不掉就永久堆积"。
- `registry.safe_unlink()`：同款兜底，供 `purge_entry` 用（避免 registry ↔ main 循环导入，故各留一份，注释互相指路）。

### 17.5 「命名」与「上传」合并成一张创建卡片

合并前是**两步两卡**：`＋ 新建数据库` 建空库 → 再滚到上方「导入价目本」卡片选目标库 + 选文件。用户诉求是把这两步合成一张卡片、一次提交。

实现（`app/QuoteApp.tsx` 的 `DatabaseForm`）：同一个表单里放**名称 / 标签 / 备注 + 价目本文件**，按钮文案随状态切换：

| 状态 | 主按钮 |
|---|---|
| 未选文件 | 创建空库 |
| 选了文件 | 创建并导入 |
| 建库成功但导入失败 | 重试导入 |
| 编辑已有库 | 保存修改 |

#### 17.5.1 补测时抓到的一个真 bug：`catch` 里读 state 读到旧值

第一轮端到端只覆盖了"重名失败"——那是在**建库那一步**就失败，`createdKey` 压根没设上。补测
"**库建好了、紧接着导入失败**"这条路径时，发现错误文案显示的是后端原始信息
（`未找到价格列（需包含 单价/价格/报价 表头）`），而不是设计的
「数据库已创建，但价目导入失败：…」——用户根本不知道库已经建出来了。

原因：`catch` 里用 `createdKey`（**state**）判断，而 `setCreatedKey(key)` 是在同一次 `submit`
调用里刚执行的，闭包读到的仍是旧值 `""`。按钮文案是对的（那是重渲染后的 state），所以只看按钮
会以为没问题。

修法：用同一次调用里的局部变量判断，而不是 state：

```tsx
let createdNow = false;
try {
  if (!key) { ...; createdNow = true; setCreatedKey(key); await onReload(); }
  ...
} catch (reason) {
  setError(createdNow || createdKey ? `数据库已创建，但价目导入失败：${message}。…` : message);
}
```

教训：**React 里"刚 set 的 state"在同一次事件处理里读不到**。凡是要在 `catch`/后续分支里
根据"刚才那步做成了没有"改行为，都必须用局部变量，不能读 state。

### 17.8 打包迁移包时顺带修掉：统计缓存不感知 WAL 写入

**发现过程**：导出「干净系统」迁移包时做 dry-run，快照里 `quote_jobs = 1`，而界面/接口的库列表却显示"任务 0"、库文件大小也停在旧值。逐步排除——

| 检查 | 结果 |
|---|---|
| 直连 SQLite（只读连接） | 1 条任务 |
| 直连 SQLite（读写连接） | 1 条任务 |
| 接口连调两次 | 都返回 0（稳定错误，不是偶发） |
| **新进程**直接调 `registry.db_stats()` | 返回 1（**正确**） |
| `touch` 源文件触发 `--reload` 清内存后 | 接口立刻变正确 |

结论：数据没问题，是**运行中进程里的缓存过期**。

**根因**：`db_stats()` 的缓存键只用**主库 mtime**。SQLite 开着 WAL 时，写入落进 `-wal`，
**主库文件的 mtime 与大小都不变** → 缓存永远命中。而"新建报价任务"这条写路径本来就没有
（也不该依赖）手动调用 `invalidate_stats`，于是计数一直错着，直到进程重启才纠正。

**修法**：`registry._stats_fingerprint()` 把 `-wal` 的 mtime 与大小一并算进指纹。
这样任何写入都会让缓存自然失效，不必在每个写入口手动失效——手动失效迟早会漏。

**回归测试**：`test_stats_are_not_stale_after_wal_only_write`。这里踩了一个坑值得记下来：
第一版测试拿**用户自建价目库**来测，结果是假阴性——报价任务行是经 `Depends(get_db)`
写进**业务库（=系统库）**的，`database_key` 只决定 `process_job` 从哪个库**读**价目，
自建库的文件自始至终没被动过。改用 `system_db_key()` 后通过，并**把修复临时改回旧行为
跑了一遍确认测试会红**（旧行为下主库 mtime/size 完全相同 —— 正是 WAL-only 写入的现场）。

**教训**：写回归测试不能只看"新代码下它通过"，还要确认"旧代码下它会失败"，否则测的是假阳性。

#### 17.9.1 一处**查到但故意没改**的地方：库列表的排序口径

前端 `sortByRecent()` 只按 `last_used_at` 排序（未使用过的是空串 → 时间戳 0），
而 `GET /api/databases` 在服务端是**有意**按 `display_name` 排的（`main.py:2527`）。
两者口径不同，看起来像 bug。

实测确认过：把 `sortByRecent` 加上 `created_at` 回落（对齐 `recent_recency()` 的口径）后，
库列表顺序**真的会变**（`赛特尔25年 → AAA → ZZZ` 变成 `ZZZ → AAA → 赛特尔25年`）。

**但这个改动被还原了。** 理由：

1. 用户没要求改排序；在即将交付的包里改变用户可见的顺序不合适。
2. "最近常用"的口径本来就不在这个列表上——它属于 `recent_entries()` /
   `GET /api/databases/search?scope=recent`（新建报价的选库入口），那里服务端已经用了
   `coalesce(last_used_at, created_at)`，是正确的。
3. 现有表现（用过的按时间倒序在前，没用过的按名称在后）本身是合理的。

**结论**：这是"口径不统一"而不是"明确的 bug"，改不改应由用户决定，已作为待确认项报给用户。
